# 课程编写规范

新增或修改课程只编辑 `content/lessons/` 中的 Markdown。正文应能独立阅读；网站里的交互负责帮助观察过程，不替代必要的概念、步骤与解释。

## 元数据

文件名必须与 `slug` 相同，例如 `example-lesson.md`。使用 UTF-8 和 LF 换行。

```yaml
---
slug: "example-lesson"
title: "课程标题"
description: "用一个具体问题说明这节课要理解什么。"
subject: "计算机基础"
order: 6
minutes: 15
lab: "bits"
objectives:
  - "解释第一个关键概念"
  - "独立完成一个具体例题"
prerequisites: ["binary-representation"]
---
```

| 字段 | 规则 |
| --- | --- |
| `slug` | 至少两个字符，小写字母开头，其余为小写字母、数字或连字符 |
| `title` | 至少两个字符 |
| `description` | 至少十个字符，说明具体学习问题 |
| `subject` | 至少两个字符，使用一致的分类名称 |
| `order` | 不重复的非负整数 |
| `minutes` | 正整数，表示预计学习分钟数 |
| `lab` | 内置实验标识，见下表 |
| `objectives` | 两至四条具体学习目标 |
| `prerequisites` | 已存在的其他课程 slug；没有先修课时写 `[]` |

不要添加未定义的元数据字段，构建会拒绝它们。先修关系应没有循环；重命名课程时，同时检查其他课程引用与旧进度的兼容性。

| `lab` | 实验 |
| --- | --- |
| `bits` | 位模式与数值解释 |
| `binary-search` | 二分查找 |
| `process` | 进程、线程与调度 |
| `javascript` | JavaScript 执行 |
| `sql` | SQLite 查询 |
| `ownership` | Rust 所有权教学演示 |
| `walkthrough` | 从 Markdown 提取的可逐步查看的例题 |

已有实验具有特定含义。新主题没有合适实验时，应扩展类型、校验规则和组件映射，不能随意套用不相关的 `lab`。

概念型课程可选择 `walkthrough`。正文必须包含 `## 逐步推演`，其后直接以三级标题开始，包含三至六个非空步骤。例如：

```markdown
## 逐步推演

### 找到输入

明确数组、目标和初始索引。

### 更新状态

写出本轮判断依据及变化后的区间。

### 检查结果

解释结果如何满足题目的条件。
```

每步应有具体数据、状态、表格或推导，不把一段介绍拆成几个空泛步骤。网站使用同一份正文呈现步骤，Markdown 本身仍可顺序阅读。它是例题讲解，不等于真实运行。

## 正文结构

一级标题介绍课程主题。页面内容按二级标题拆分，主要讲解不要放在第一个二级标题之前。标题直接使用普通文字，避免依赖内联标记作为解析标识。

推荐先写具体问题和必要概念，再给步骤、例题、实验、常见错误和练习。段落面向初学者，先解释符号和条件，再使用公式；面试短答是理解后的总结。

首次解释专有名词时采用“中文（English Full Name，缩写）”，例如“中央处理器（Central Processing Unit，CPU）”。没有通用缩写时只补英文名称；后文可用中文或缩写，不重复堆叠翻译。普通中文词语不需要逐个翻译。

面试短答集中说明定义、机制、条件与限制；详细推导放入正文。每课讲清一个紧密相关的问题，不用合集式题目列表代替教学。涉及易混概念时明确比较维度，并至少提供一个具体反例或错误原因。

以下标题有固定含义，名称须保持一致：

- `## 面试回答`：必需，集中说明定义、机制和关键限制。
- `## 实验代码`：需要代码实验时提供；第一个围栏代码块作为实验初始代码。
- `## 选择题`：必需，按下述格式提供一道四选一题。

其他二级标题自由命名。可增加例题、解题过程、错误示例、开放追问和参考资料，不必为每课机械填满相同栏目。

## 选择题格式

第一段是完整题干，四个列表项依次使用 `A.` 到 `D.`，答案段以 `答案：` 开头。

```markdown
## 选择题

8 位无符号整数能够表示多少种不同的值？

- A. 8 种
- B. 128 种
- C. 255 种
- D. 256 种

**答案：D。** 每位有两种状态，共有 2 的 8 次方种组合。
255 是最大值，计数还要包含 0。
```

解释应说明正确答案的原因，并指出有代表性的错误选项为什么不成立。不要把答案只写成字母，也不要在同一 `选择题` 小节塞入多道题。

## 示例与技术正确性

- 写清位宽、区间开闭、索引起点、语言或数据库环境等必要前提。
- 推导展示中间状态，例如每轮搜索区间、每条连接记录的匹配过程。
- 代码应短小完整；输出必须来自相应环境中的执行，未执行结果只能标为预期。
- 报错示例解释触发条件与修改原因；不要将未定义行为描述为固定输出。
- 不依赖对象地址、线程调度或计时精度产生唯一答案。
- SQL 练习按 SQLite 编写，涉及其他数据库时明确差异。
- Rust 诊断参考说明对应代码和规则，不声称在线完成了编译。
- 引用支持当前结论的语言规范、协议标准、官方文档或公开教材资料。
- 正文不包含私人经历、聊天记录、制作过程或无关的工具说明。

禁止原始 HTML、JSX、内联事件和外部脚本。使用标准 Markdown 链接、表格及带语言标记的围栏代码块；代码块里的标记按示例文本展示。

## 提交前检查

```powershell
npm run content
npm run check
npm test
npm run build
```

逐一检查命令退出码。在页面上读完修改过的课程，完成练习，验证实验与下载的 Markdown 内容一致；若修改运行器，还需验证错误、停止和超时。

检查生成结果可以发现解析问题，但不要手改生成文件。新增或删除文件后，如果开发页面没有更新，重新运行内容构建并重启开发服务。
