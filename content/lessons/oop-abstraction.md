# 抽象：用户需要知道什么

## 先看一个队列契约

抽象（Abstraction）是从具体实现中提取使用者真正需要的性质。一个先进先出（First In, First Out，FIFO）队列可以承诺：`enqueue(x)` 把元素放到尾部；`dequeue()` 取出最早尚未取出的元素；空队列的 `dequeue()` 明确报告“无元素”。使用者只依赖这些行为，不必知道里面采用数组、链表还是其他结构。

契约（Contract）还要说清边界：元素顺序、空队列结果、操作是否可失败。只写“提供 enqueue 和 dequeue 两个函数名”不够；若实现偷偷从尾部弹出，就变成栈，违背队列抽象。[Java `Queue` 官方 API：队列操作契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Queue.html)

## 逐步推演

### 第一步：只对外展示操作

假设接口写成 `enqueue(String item)` 和 `dequeue() -> Optional<String>`。这里 `Optional` 用来区分“空队列”和真实字符串值；不讨论并发阻塞。调用者执行 `enqueue("A")`、`enqueue("B")`，抽象状态是从队首到队尾 `[A, B]`。

### 第二步：按契约取值

第一次 `dequeue()` 应得到 `A`，队列变 `[B]`；第二次得到 `B`，队列变 `[]`；第三次得到空结果。若实现用数组，可能移动起点索引；若用链表，可能移动头指针。调用者不应凭队列抽象猜测具体做了哪一个动作。

| 操作 | 对外结果 | 抽象状态 |
| --- | --- | --- |
| 入队 A、B | 成功 | `[A, B]` |
| 第一次出队 | `A` | `[B]` |
| 第二次出队 | `B` | `[]` |
| 第三次出队 | 空结果 | `[]` |

### 第三步：更换实现但保留行为

把内部从链表改为可增长数组，只要给相同操作序列的可观察结果仍满足 FIFO 与空队列规则，使用者代码就不必因内部表示变化而重写。反例：新实现把 `B` 先返回，虽然方法签名没有变，却破坏了抽象契约。

### 第四步：分清抽象与封装

抽象侧重**选择并约定对外有意义的行为**；封装侧重把内部状态与维护规则的操作放在一起，限制外界绕过规则。队列可以有清晰的 FIFO 抽象，却因暴露可变内部数组导致封装被破坏；也可以把所有字段设成 `private`，却没有解释空队列语义，抽象仍不完整。

## 面试回答

抽象是把复杂实现压缩成用户可依赖的行为契约。以队列为例，调用方关心入队、出队、FIFO 顺序及空队列结果，而不用知道数组或链表细节；换实现必须保留这些可观察行为。封装更关注保护内部状态和约束访问，二者相关但不等同。好的抽象不只是起一个接口名，还要写清边界条件与失败语义。

## 常见错误

- **“有接口关键字就一定有好抽象。”** 接口仍可能没有明确顺序、错误或状态约定。
- **“内部换实现后方法名没变，就一定兼容。”** 行为和边界也必须保持契约。
- **“抽象就是把字段设成 private。”** 访问控制是封装工具，不能替代对外行为定义。
- **“所有语言的抽象都必须用 Java interface。”** C 可用函数表或模块 API，Rust 可用 trait，机制并不相同。

## 选择题

一个队列连续入队 A、B 后，第一次出队返回 B，第二次返回 A。哪项最准确？

- A. 只要函数名是 dequeue，就满足 FIFO 抽象
- B. 它违背本课约定的 FIFO 行为契约
- C. 它只是把数组实现换成链表实现
- D. 空队列结果决定了它必然正确

**答案：B。** FIFO 要先返回先入队的 A。A 忽略行为，C 无法由返回顺序推出实现，D 与当前非空操作无关。
