# 索引：怎样少检查一些记录

## 从零理解

索引（index）是数据库维护的辅助查找结构，包含键值和定位相应数据所需的信息。
查询成绩表时，`WHERE student_id = 1` 描述了目标，但不指定数据库必须如何找到它。
没有合适索引时，可能需要全表扫描（full table scan），逐行检查学生编号。
记录很多且只有少数符合条件时，大量检查最后都没有产生结果。

本课用普通 SQLite 行号表（rowid table）。没有特殊声明的这种表，记录有内部整数行号 `rowid`。
SQLite 的普通索引使用 B 树（B-tree）结构；本课只画有序索引项，不把平面表格当成实际树结构。
索引按键组织信息，使数据库能够定位一个范围，然后只继续读取相关记录。
这需要额外空间；插入、删除或改动索引键时，也需要维护索引。

## 具体问题

在一张名为 `grades` 的示例表中，查找学生 1 的所有分数。

| rowid | student_id | score |
| --- | --- | --- |
| 1 | 3 | 70 |
| 2 | 1 | 80 |
| 3 | 2 | 60 |
| 4 | 1 | 90 |
| 5 | 4 | 75 |

这五行只用于看清路径，不用于证明性能提升。查询目标是 `(1,80)` 与 `(1,90)`。
如果把数据扩大到大量记录，扫描与定向查找之间的工作量差异才更容易观察。

## 逐步推演

### 第一步：没有索引时检查每行

依次检查学生编号 `3 → 1 → 2 → 1 → 4`。
第 2、4 行匹配，其他三行丢弃；共检查五条记录，得到两条结果。
扫描能得到正确答案，它的问题是即使只要少量记录，也可能要检查很多无关记录。

### 第二步：建立按学生编号组织的索引

```sql
CREATE INDEX idx_grades_student ON grades(student_id);
```

索引项可按下表理解；相同学生编号用内部行号区分记录。

| student_id | rowid |
| --- | --- |
| 1 | 2 |
| 1 | 4 |
| 2 | 3 |
| 3 | 1 |
| 4 | 5 |

索引按查找键组织，但不会因此把所有查询的输出顺序变成按学生编号排序。

### 第三步：定位匹配范围，再取成绩

在索引中定位学生编号 1，找到对应内部行号 2、4。
这个索引没有保存 `score`，还需要根据行号读取相应表记录，取得 80 和 90。
用索引找到键不等于查询已经获得全部输出列；少查索引之外的记录也是减少工作的来源。

### 第四步：比较收益与代价

若查询几乎需要整张表，逐条通过索引再读取表记录未必比直接扫描划算。
若给学生 1 新增一条 85 分记录，数据库除了写表，还要插入对应索引项。
所以要同时考虑读请求的频率、筛选范围、输出列以及写入维护，而不是给每列都建立索引。

## 可以核对的执行计划

查询计划（query plan）说明数据库打算采用的访问方式，不是运行耗时报告。
在上表数据已经准备好的 SQLite 数据库中，可以执行：

```sql
EXPLAIN QUERY PLAN
SELECT student_id, score
FROM grades
WHERE student_id = 1;
```

没有索引时通常会看到扫描；创建索引后可能看到使用该索引的搜索。
具体文本、选择策略受版本、统计信息和表结构影响，不能把某条计划字符串当作所有数据库的固定答案。
比较性能还需要相同输入、数据规模和环境下的实际测量；五行示例不适合判断速度提升比例。

## 进一步理解覆盖索引

若建立 `(student_id, score)` 复合索引（composite index），本例所需列可能都能从索引中取得。
这样的查询可使用覆盖索引（covering index），减少再查表记录的工作。
索引键先按 student_id 再按 score 排列，因此它不等同于单独对 score 建立的索引。
能否高效支持某个条件，要结合键顺序和数据库优化方式，不能只看“这个列在索引里面”。

## 常见错误

- **索引必然提高速度。** 很小的表、返回大部分行的查询和频繁写入都可能使收益有限。
- **命中索引就不用读表。** 还要看需要的列是否已经由索引提供。
- **索引自动保证唯一。** 普通索引允许重复键；唯一性需要唯一索引或相应约束。
- **使用索引结果自然有序。** 需要稳定结果顺序，查询仍应明确写 `ORDER BY`。
- **索引查找永远 O(1)。** 普通树索引需要沿结构查找，还要考虑返回记录数和存储访问。

## 面试回答

索引保存有组织的键和记录定位信息，让数据库可能通过少量定位工作找到匹配范围，减少无关记录的扫描。
它占用空间，并增加写入维护成本；是否更快由查询、数据分布、输出列和执行计划决定。
覆盖索引可以直接提供查询所需数据，但不是所有索引查询都能避免继续读取表记录。

## 选择题

索引只包含 `student_id` 和记录定位信息，查询要返回 `score`。哪个判断正确？

- A. 一定可以仅从这个索引读出所有成绩。
- B. 找到匹配索引项后，仍可能需要读取表中的成绩。
- C. 创建索引会自动删除重复的 student_id。
- D. 查询结果从此永远按 student_id 排序。

**答案：B。** 索引没有提供 `score`，需继续取得该列。A 忽略输出列；C 混淆普通索引与唯一约束；D 把访问方式当成结果排序保证。

## 面试追问

“为什么写入变慢？”维护主表之外，还要更新相关索引，可能涉及页修改和空间调整。
“如何判断是否值得建立？”先找频繁查询及其条件，观察数据量、匹配比例和执行计划，再测量读写变化。
“匹配比例很低就一定用索引吗？”不一定；优化器还会比较查表、排序、存储访问等成本。
