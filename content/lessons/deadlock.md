# 死锁与锁获取顺序

## 面试回答

死锁（Deadlock）是一组执行者相互等待，使它们在现有资源和释放规则下无法继续的状态。在经典可重用资源模型中，发生死锁需要互斥、占有且等待、不可抢占、循环等待四个条件。处理方式包括破坏某个条件以预防死锁、根据安全性判断避免进入危险状态，以及检测后恢复。使用多把锁时，统一获取顺序可以排除相应锁集合的循环等待；仅增加线程或处理器数量不能解决已经形成的等待环。

## 从零理解“正在等”和“永远等”

线程 A 持有锁 X 做计算，线程 B 等 X。如果 A 能完成并释放，B 仍有继续的可能，这只是正常等待。

若 A 只有拿到 Y 才会释放 X，而持有 Y 的 B 又只有拿到 X 才会释放 Y，继续执行的前提就互相卡住了。

本课设定两把普通互斥锁 X、Y，各只有一个实例；线程成功获取后一直持有到显式释放，没有超时、外部强制终止或其他释放者。这些前提决定下面的等待环为何无法自行解除。

## 四个条件要结合具体状态理解

| 条件 | 英文名称 | 本例中的含义 |
| --- | --- | --- |
| 互斥 | Mutual Exclusion | X 或 Y 同时只能由一个线程持有 |
| 占有且等待 | Hold and Wait | 已经持有一把锁，仍等待另一把 |
| 不可抢占 | No Preemption | 不能由等待者强行夺走别人持有的锁 |
| 循环等待 | Circular Wait | A 等 B 的资源，B 又等 A 的资源 |

这里的“不可抢占”描述资源回收规则，不是说操作系统不能抢占线程的中央处理器（Central Processing Unit，CPU）时间。调度器暂时停下持锁线程，不会自动把它的锁安全地交给别人。

允许这四种条件同时存在，说明系统有发生死锁的可能；不能据此断言任意一次执行都一定死锁，还要看实际资源与等待关系。

## 逐步推演

### 第一步：两个线程分别拿到一把锁

A 按“先 X 后 Y”的顺序获取锁，B 按“先 Y 后 X”的顺序获取锁。现在恰好交错到：

| 线程 | 已持有 | 下一步 |
| --- | --- | --- |
| A | X | 尝试获取 Y |
| B | Y | 尝试获取 X |

此时两者还各自拿着有用的资源。错误不在单次获取动作，而在两个获取顺序相反。

### 第二步：等待关系形成环

A 尝试获取 Y，但 Y 在 B 手里；B 尝试获取 X，但 X 在 A 手里。

```text
A 持有 X，等待 B 释放 Y
B 持有 Y，等待 A 释放 X
等待关系：A -> B -> A
```

两者都没走到释放语句，却都需要对方先释放。根据本课没有超时或外部回收的前提，这个状态已经是死锁，继续轮流调度也不能产生新的可执行获取动作。

### 第三步：重新运行，统一先 X 后 Y

这一步从未持锁的初始状态重新开始；不是只修改代码就能自动解救已经卡住的线程。

| 动作 | X 持有者 | Y 持有者 | 等待者 |
| --- | --- | --- | --- |
| A 先取得 X | A | 无 | 无 |
| B 也尝试 X | A | 无 | B 等 X |
| A 继续取得 Y | A | A | B 等 X |

B 还没有获得任何锁，不会占着 Y 阻挡 A。A 因此可以进入同时需要两把锁的操作。

### 第四步：A 完成后，B 才继续

假设 A 的临界区能够正常结束，并释放已经持有的锁：

| 动作 | X 持有者 | Y 持有者 |
| --- | --- | --- |
| A 释放 Y、X | 无 | 无 |
| B 获得 X | B | 无 |
| B 获得 Y | B | B |
| B 完成并释放 | 无 | 无 |

现在可能存在等待，但不存在刚才的持锁等待环。统一顺序破坏的是循环等待条件，不是取消锁的互斥能力。

## 为什么统一顺序能够排除这个环

为所有相关锁规定严格顺序，例如 `X < Y < Z`，每个线程都只能按顺序向后获取，不能持有较大的锁再等待较小的锁。

沿一条持锁依赖链前进时，锁的编号只能越来越大。如果形成环，就必须最终回到更小的起点，这与规则矛盾。

这个结论有边界：所有相关代码路径都必须遵守同一顺序，回调或隐藏的加锁也不能违反它。重复获取一把不可重入锁，还可能让单个线程等待自己，不能靠“有统一顺序”忽略这种情况。

Linux 的锁依赖检查会观察锁之间的获取关系，帮助发现潜在反向依赖；它是检测工具，不能代替程序对资源生命周期的设计。

## 资源图里有环，一定死锁吗

在每类资源只有一个实例的经典资源分配图中，实际等待环可以判定死锁。本课的 X、Y 就满足这个前提。

若同类资源有多个实例，仅看到一个环还不够：某个环外任务可能释放另一个可用实例，让环中的任务继续。面试时应先说明资源模型，不能把单实例结论直接推广。

## 常见误解

- **“线程长时间没有响应，就是死锁。”** 也可能在等待慢设备、执行长计算或遭遇饥饿，需要检查等待关系。
- **“多加一个 CPU 核心就能同时拿到锁。”** 互斥规则仍然存在，已经形成的等待环不会因此消失。
- **“超时自动解决所有问题。”** 超时后还需释放已有资源、恢复一致状态，并设计后续重试规则。
- **“给每把锁都加一个锁。”** 若新的获取顺序仍有循环，只是把问题移到了另一组锁。

## 选择题

A、B 都需要 X、Y 两把互斥锁。要求所有线程先获取 X 再获取 Y，主要破坏哪个死锁必要条件？

- A. 互斥
- B. 占有且等待
- C. 不可抢占
- D. 循环等待

**答案：D。** 统一顺序阻止“持 Y 等 X”这类反向依赖。X、Y 仍然互斥，线程仍可能持 X 等 Y，锁也没有因此变成可强行抢占的资源。

## 面试追问

**死锁、饥饿和活锁怎样区分？**

死锁参与者因相互依赖无法前进；饥饿（Starvation）是某个任务长期得不到机会，而其他任务仍能推进；活锁（Livelock）是任务持续改变状态或重试，却没有完成有效工作。它们都可能表现为“没完成”，机制不同。

**预防和避免有什么差别？**

预防通过规则破坏某个必要条件，例如统一锁顺序；避免则在资源分配前利用所需信息检查后续是否仍存在安全完成顺序。安全状态不是说当前所有任务都能立刻执行，不安全状态也不等于此刻已经死锁。
