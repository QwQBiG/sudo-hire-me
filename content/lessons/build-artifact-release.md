# “构建通过了”到底说明什么

## 同一份代码有几个不同的关口

以一个很小的 C 命令行程序为例：`main.c` 调用 `parse.c` 中的解析函数，`parse.h` 声明接口。编译器分别处理源文件，生成目标文件；链接器把目标文件和需要的库组合成可执行文件。之后还要运行测试，最后才把确定的产物交给发布流程。**构建成功**通常说明编译、链接等步骤完成，不自动说明程序对所有输入都正确、也不说明部署环境一定可运行。

在现代项目里，构建系统还可能生成资源、执行代码生成或打包；这里先用最基础的 C 模型看清各关口，不把某个工具的命令当成所有语言都相同。[GCC 文档：编译与链接选项](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)

## 逐步推演

### 第一步：接口不一致会在不同阶段暴露

假设 `parse.h` 声明 `int parse(const char *text);`，`main.c` 调用它，而 `parse.c` 不小心没有提供匹配的定义。若头文件让调用方通过语法/类型检查，编译 `main.c` 可能成功；链接时却找不到需要的符号，得到未定义引用一类错误。若调用参数类型与可见声明不匹配，问题则可能更早在编译阶段被报告。具体诊断文字取决于工具链，但**发现问题的阶段**可以区分。

| 阶段 | 典型输入 | 典型产物 | 本例可能失败的原因 |
| --- | --- | --- | --- |
| 编译 | `main.c`、`parse.c`、头文件 | 目标文件 | 语法错误或可见类型不匹配 |
| 链接 | 目标文件与库 | 可执行文件 | 缺少 `parse` 定义 |
| 测试 | 可执行文件与测试输入 | 断言结果 | 解析错误或边界处理不对 |

### 第二步：可执行文件产生后还要测行为

修正 `parse` 定义后，程序成功生成。测试给它正常输入和错误输入：正常行应被解析，格式不合法的行应按约定返回错误。若两者之一不符合预期，这是行为问题，不是“链接器坏了”。修复后重新构建并重跑直接相关测试，不能只复用上一次生成的旧可执行文件。

### 第三步：打包的是哪一份结果

设提交 A 构建出的程序通过测试，随后提交 B 修改了解析函数。如果发布时拿错了上一次构建的产物，就可能出现“源码看起来是 B，运行的却是 A”。发布记录应能关联源码提交、构建配置、依赖版本和产物标识，使问题发生时能确定用户实际运行的版本。必要时记录校验和来核对产物未被意外替换。

相同源码也可能因编译器版本、构建选项、依赖或环境而生成不同结果；“版本号一样”不足以证明字节完全相同。可复现构建需要额外控制这些输入，本课不把普通构建自动等同于字节级可复现。

### 第四步：发布后仍要观察

产物在测试机器通过，不代表在目标机器上能找到相同动态库、配置和权限。发布后应检查程序启动、关键路径和错误日志；失败时先确认实际部署的产物，再定位环境差异或行为回归。构建、测试、部署和运行时观察各有独立证据，不能用“流水线绿色”代替一切。

## 面试回答

源码通常先经编译生成目标文件，再经链接形成可执行产物；编译/链接成功只证明这些步骤能完成，行为正确还要靠测试。发布时我会把产物与源提交、构建配置和依赖版本关联，确保部署的是测过的那份；在目标环境还需验证启动与关键路径。遇到问题先判断失败发生在编译、链接、测试、部署还是运行阶段。

## 对不同语言怎样迁移这个模型

Python 3 的常见部署不需要像本例这样链接成本机可执行文件；Java/Kotlin 常涉及字节码和运行时；Rust、Zig、C++也有各自的构建与链接细节。共通的是**明确输入、产物、验证和部署版本**，不是强行把每种语言都说成 C 的编译链。

## 常见误区

- **“编译成功就表示没有逻辑错误。”** 编译器一般不知道业务预期。
- **“未定义引用是运行时业务错误。”** 通常应先查链接阶段的定义和依赖。
- **“测过源码，所以任何旧产物都安全。”** 测试必须对应将要发布的具体产物。
- **“同一提交必定产生完全相同的二进制。”** 还受工具链、选项和依赖影响。

## 选择题

`main.c` 成功生成目标文件，但最终可执行文件因找不到 `parse` 的定义而失败。最直接应检查哪一阶段？

- A. 链接阶段是否包含正确的定义与目标文件。
- B. 用户点击按钮是否太快。
- C. 只检查 CSS 样式。
- D. 宣布所有测试已通过。

**答案：A。** 调用方的目标文件已有，但链接器找不到实现；B、C、D 与错误发生的阶段不符。
