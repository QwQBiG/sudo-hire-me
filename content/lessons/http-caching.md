# HTTP 缓存与条件请求

## 面试回答

HTTP 缓存（HTTP Cache）保存可复用的响应，减少重复获取资源的开销。缓存先判断是否允许保存，以及响应是否仍然新鲜；满足复用条件时可直接使用。需要验证时，可以携带实体标签（Entity Tag，ETag）等验证器发起条件请求。资源未改变时，服务器可以返回 304，客户端复用已有正文并更新缓存元数据；改变时通常返回 200 和新正文。`no-cache` 允许保存，但复用前必须成功验证；`no-store` 要求不保存本次响应，不等于清除所有旧缓存。

## 先分清三个问题

浏览器已经下载过文件，并不意味着之后可以永远使用同一份副本。

| 问题 | 对应判断 | 示例 |
| --- | --- | --- |
| 能不能保存 | 存储条件与缓存指令 | `no-store` 禁止保存这次响应 |
| 现在能否直接复用 | 新鲜度（Freshness）与其他请求条件 | `max-age=60` 限定新鲜寿命 |
| 旧副本是否仍匹配 | 验证（Validation） | 用 ETag 询问源站当前版本 |

源站（Origin Server）是负责给出资源权威表示的服务器。私有缓存（Private Cache）面向单个用户，例如浏览器缓存；共享缓存（Shared Cache）可服务多个用户，例如某些代理缓存。

本课只推演浏览器中一个可缓存的 GET 响应，没有认证、范围请求、代理、网络时延或其他缓存副本。实际协议还要考虑更多存储和复用条件。

## 一次完整响应留下什么

首次请求没有副本，服务器返回：

```http
HTTP/1.1 200 OK
Cache-Control: max-age=60
ETag: "v1"
Content-Type: application/json

{"version":1}
```

缓存控制（Cache-Control）响应字段中的 `max-age=60` 指定响应新鲜寿命为 60 秒。ETag 是服务器为选定表示提供的不透明验证标识，不保证是哈希值，也不需要客户端理解它的内部含义。

这里假设响应刚产生就被浏览器保存，初始年龄为零。真实响应年龄还可能包含上游已缓存时间、网络延迟等因素，不能把真实 HTTP 的年龄一律简化成“下载到本机后的秒数”。

## 新鲜时，源站改变了也未必立刻知道

使用上述简化前提，新鲜判断为：

```text
当前年龄 < 新鲜寿命
30 秒 < 60 秒：仍然新鲜
60 秒 < 60 秒：不成立，已经不新鲜
```

假设第 20 秒源站把资源改成 v2，第 30 秒浏览器再次访问。没有其他强制验证要求时，浏览器仍可复用新鲜的 v1。

这不是缓存“忘了检测变化”，而是当前策略允许一定时间内复用。源站发生修改不会自动把更新推送到每个浏览器；需要结合业务选择缓存寿命。

通常所说的“强缓存”是直接复用新鲜响应的一种面试表达，并非另一个 HTTP 状态码。开发者工具中看到 `200 (from memory cache)` 等标记，不代表源站又发送了一次 200 响应。

## 过期后，先问版本有没有变化

第 60 秒再次访问，浏览器有 v1 的正文和验证器，可以发送条件请求（Conditional Request）：

```http
GET /lesson.json HTTP/1.1
Host: www.example.com
If-None-Match: "v1"
```

`If-None-Match` 表达：当当前选定表示的标签不匹配给定标签时，才执行通常的获取处理。对于这里的 GET，标签匹配会触发“未修改”响应。

如果服务器仍然是 v1，可以返回：

```http
HTTP/1.1 304 Not Modified
Cache-Control: max-age=60
ETag: "v1"
```

304 不携带资源正文。浏览器用现有正文满足读取，并按规则更新元数据。它节约了正文传输，但仍然发生了与服务器的通信，不能说“协商缓存完全不联网”。

如果服务器已经变成 v2，则返回 200、新验证器和新正文。客户端用新响应更新缓存；不能把“过期”直接等同于“一定下载完整内容”。

## 把一次生命周期算清楚

下面仍忽略传输时延，验证成功后的新鲜寿命保持 60 秒。

| 时刻 | 浏览器已有副本 | 源站版本 | 请求结果 |
| --- | --- | --- | --- |
| 0 秒 | 无 | v1 | 200，保存 v1，年龄归零 |
| 30 秒 | v1，年龄 30 秒 | v1 | 本地复用，不联网 |
| 60 秒 | v1，年龄 60 秒 | v1 | 条件请求得到 304，复用正文 |
| 70 秒 | v1，验证后年龄 10 秒 | v2 | 本地仍可复用 v1 |
| 120 秒 | v1，验证后年龄 60 秒 | v2 | 条件请求得到 200，保存 v2 |

重点不是记住这些固定时刻，而是每次先问“当前副本是否可直接复用”，需要验证时再比较服务器上的表示是否改变。

## no-cache 与 no-store 不要靠字面猜

| 响应指令 | 是否可以保存 | 再次复用前 |
| --- | --- | --- |
| `max-age=60` | 满足其他条件时可以 | 新鲜期内通常无需验证 |
| `no-cache` | 可以 | 必须成功验证，即使刚刚保存 |
| `no-store` | 不应保存本次响应 | 本次响应不形成可复用副本 |

例如经常变化、但体积较大的文档，可以允许保存并要求验证；验证器没变时仍可能节省正文传输。敏感数据的存储策略还需结合访问控制与产品要求，不能把一个指令当成完整隐私方案。

`no-store` 不是远程清除所有历史缓存的命令，也不能保证每个不遵守协议的中间方都没有保存信息。

## ETag 之外还会问什么

最后修改时间（Last-Modified）也可作为验证依据，客户端相应发送 `If-Modified-Since`。时间验证可能受精度和实现规则限制；不要直接把文件系统时间戳当成无条件正确的版本号。

同时存在 `If-None-Match` 与 `If-Modified-Since` 时，服务器按协议优先处理前者；不能把两者理解为两个互不相关、必须同时满足的下载开关。

`Vary: Accept-Language` 表示响应选择依赖请求的 `Accept-Language` 字段。缓存不能仅因为 URL 一样，就把英文版本当成中文请求的等价副本。

查询字符串属于请求目标，可以影响缓存键（Cache Key）。添加参数并不天然意味着“不可缓存”，它也可能只是形成另一个缓存条目。

## 常见误解

- **“304 是一次失败。”** 对这里的条件 GET，它是验证匹配的有效结果，正文来自已有副本。
- **“有 ETag 就永远先验证。”** 仍然新鲜且满足复用条件时，可以直接复用；ETag 不自动取消新鲜寿命。
- **“资源过期就必须删除文件。”** 不新鲜的副本仍可参与验证，并在 304 后继续使用正文。
- **“no-cache 就是不缓存。”** 它约束复用前验证，不禁止保存。

## 选择题

本课模型中，浏览器保存的响应为 `Cache-Control: max-age=60`、`ETag: "v1"`，当前年龄恰好为 60 秒，服务器仍是 v1。没有其他特殊指令，最符合规则的处理是哪项？

- A. 因为年龄等于 60，仍可作为新鲜响应直接复用
- B. 发出携带验证器的条件请求，得到 304 后复用已有正文
- C. 服务器返回 304，同时必须再次附带全部正文
- D. ETag 存在，所以缓存永远不会过期

**答案：B。** 新鲜判断使用“小于”，等于寿命时已经不新鲜。304 表示这里的条件验证匹配，不携带资源正文。ETag 解决表示验证问题，不延长 `max-age` 指定的新鲜寿命。

## 面试追问

**为什么发布后有的用户还看到旧文件？**

先检查是否仍允许直接使用新鲜副本，再看 HTML、静态资源与中间缓存各自的策略。内容指纹文件名可让内容变化对应新 URL，但仍要确保引用这些 URL 的入口页面能及时更新。

**按刷新按钮就一定执行同一套缓存行为吗？**

不能把浏览器的普通刷新、强制刷新或开发者工具选项当成一条统一协议规则。应观察实际请求头、缓存来源和响应状态，再用新鲜度与条件请求语义解释。
