# 开源经历怎么讲，才不只剩一个链接

## 贡献过程比仓库名更重要

面试官可能问“你给开源项目贡献了什么”。只报项目名和一个链接，无法说明技术工作。需要讲清问题怎样发现、怎样确认它属于项目范围、修改了什么、如何验证，以及维护者提出过什么意见。拉取请求（Pull Request，PR）是**提议合并修改**，打开 PR 不等于已合并；已合并也不自动表示某个已发布版本已经包含它。[GitHub 文档：协作修改与拉取请求](https://docs.github.com/en/pull-requests/concepts/writing-code-for-a-project)

下面仍用虚构的解析库修复说明结构，不代表任何人的真实贡献：输入末尾有空行时，库错误地生成一个空记录。贡献者补最小复现测试，修正末尾处理，在 PR 中说明行为并根据评审调整测试命名。

## 逐步推演

### 第一步：确定问题与预期行为

先阅读项目已有说明和测试，确认末尾空行按项目约定应被忽略，而不是自己认为“应该忽略”。保留最小输入：`a,b\n` 与 `a,b\n\n`；观察返回记录数，说明哪个输入使错误出现。若行为文档没有规定，应先在 issue 或讨论中确认，不把个人偏好强行写成项目规则。

若已有 issue，说明自己是在复现已有问题；若由自己发现，也要区分“报告问题”和“提交修复”是两个动作。

### 第二步：描述具体改动与范围

可以说：“我在行结束判断处区分普通记录与文件末尾空行，补了一组回归测试；没有修改其他格式的解析规则。”这句话能让面试官追问分支条件、边界输入和为什么范围这样定。若只是改文档、测试或错误信息，也应准确命名，不需要包装成“重写整个解析器”。

分支（Branch）和复刻仓库（Fork）是隔离改动的方式；没有上游写权限时经常在 fork 中工作，有权限时也可用同仓库分支。提交（Commit）记录改动快照，PR 把改动和说明交给上游讨论；它们不是同一个状态。[GitHub 文档：分支、fork 与 PR](https://docs.github.com/en/pull-requests/concepts/writing-code-for-a-project)

### 第三步：把评审反馈讲成技术问题

假设维护者指出：原测试只覆盖文件末尾一个换行，却没覆盖两个换行。贡献者补第二个输入，并说明两者预期不同的原因。面试中值得讲的是“反馈暴露了哪个遗漏、我怎样修改、验证了什么”，而不是只说“维护者让我改了两次”。如果反馈涉及与原目标无关的重构，应说明是否另开任务，而非把范围扩张说成原计划。

PR 的评审可能是评论、批准或请求修改；这些表示讨论状态，不等同于代码已进入主分支。[GitHub 文档：PR 评审](https://docs.github.com/en/pull-requests/concepts/giving-reviews)

### 第四步：准确报当前状态与结果

可以按事实说“补丁已提交，等待评审”“根据评审增加测试，尚未合并”“已合并到主分支，但我没有核实发布版本”，或“已在某版本发布，版本号和变更记录可查”。不要把“PR 打开”说成“社区已经采用”，也不要拿 star 数代表自己的代码质量。真实讲述应能找到对应的变更、测试或讨论记录。

## 面试回答

我介绍开源贡献会从真实问题和最小复现开始，讲自己修改的代码或文档范围、验证方式及评审反馈，再准确说明目前是提交、评审、合并还是已发布。团队和维护者的工作与自己的提交分开说；即使补丁很小，也能围绕边界、测试和技术取舍讲清价值。

## 追问准备

把 PR 页面当作索引，而不是答案本身。提前能解释：为什么这几行需要改、旧行为具体错在哪、怎样证明没有破坏正常输入、评审中的替代方案是什么。若上游最终没有合并，仍可诚实讲复现、实现与反馈，并说明未合并的真实原因；不把未合并自动等同于失败或成功。

## 常见误区

- **“我提了 PR”就说“功能已经上线”。** 提议、合并、发布是不同阶段。
- **用仓库影响力替代个人工作。** 仓库受欢迎不说明自己改了什么。
- **只说改了几行，不解释行为变化。** 行数不能解释正确性和边界。
- **把评审当成形式。** 技术反馈和补充验证往往是贡献中最值得说明的部分。

## 选择题

一项 PR 已打开，测试通过，但维护者尚未完成评审。怎样表述最准确？

- A. “这个功能已发布，用户都在使用。”
- B. “我提交了补丁和测试，当前等待维护者评审；还不能说已经合并。”
- C. “测试通过就自动等于主分支接受了代码。”
- D. “仓库有很多 star，所以我的修改一定没有问题。”

**答案：B。** 它把已完成的工作与仍待确认的状态分开；A、C 把不同阶段混同，D 用无关指标替代验证。
