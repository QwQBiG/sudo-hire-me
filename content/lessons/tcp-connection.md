# TCP 建连与关闭

## 面试回答

传输控制协议（Transmission Control Protocol，TCP）的典型三次握手用于建立双方连接状态、交换并确认初始序列号。双方先后发送同步序列号标志（Synchronize，SYN），并通过确认标志（Acknowledgment，ACK）确认对方序列号。关闭时两个发送方向分别结束，因此常见过程包含两个发送结束标志（Finish，FIN）及相应确认，通常称为四次挥手；确认和 FIN 可以合并，所以报文数量并非固定。典型主动关闭方经过 TIME_WAIT 状态后再彻底释放连接状态。

## 从零理解“连接状态”

TCP 连接不是一根新铺设的电线，而是双方共同维护的一组信息：通信端点、发送到哪里、收到了哪里、缓冲与计时状态等。

客户端和服务器各维护自己的状态。一方认为连接建立，不代表另一方在完全相同的时刻已经知道这件事；报文存在传播延迟，也可能丢失。

本课使用典型的主动打开与被动监听场景。假设握手报文没有携带应用数据，客户端初始序列号（Initial Sequence Number，ISN）为 1000，服务器为 5000；数值仅为教学示例。

## 先看懂两个数字

序列号（Sequence Number，记作 `seq`）标识本段内容在发送方向上的位置。确认号（Acknowledgment Number，记作 `ack`）通常表示接收方下一步期望收到的序列位置。

| 内容 | 占用序列号空间吗 |
| --- | --- |
| 一个应用数据字节 | 占用 1 |
| SYN 标志 | 占用 1 |
| FIN 标志 | 占用 1 |
| 没有数据、SYN 或 FIN 的纯 ACK | 不占用 |

确认号 `1001` 是一个数值，ACK 则是表明确认字段有效的标志，不要把二者混为一谈。两个方向分别维护序列号，服务器不需要沿用客户端的起点。

## 逐步推演

### 第一步：客户端发送 SYN

客户端发送 `SYN, seq=1000`，进入 `SYN-SENT`，等待服务器响应。

| 一方 | 当前知道什么 |
| --- | --- |
| 客户端 | 自己发出了建连请求，还未确认服务器的序列号 |
| 服务器 | 收到请求后知道客户端起点为 1000 |

服务器原先处于监听状态。收到可接受的请求后，它需要给出自己的起点，并确认客户端的 SYN。

### 第二步：服务器发送 SYN 与 ACK

服务器返回 `SYN + ACK, seq=5000, ack=1001`，进入 `SYN-RECEIVED`。

```text
确认客户端的 SYN：1000 + 1 = 1001
公布服务器的初始序列号：5000
```

客户端收到后，既知道自己的 SYN 已被确认，也知道服务器的起点。但服务器还没有收到“客户端已接受服务器起点”的确认。

### 第三步：客户端确认服务器起点

客户端发送 `ACK, seq=1001, ack=5001`。本例中它进入 `ESTABLISHED`；服务器收到可接受的确认后，也进入 `ESTABLISHED`。

| 方向 | 下一应用数据的序列起点 |
| --- | --- |
| 客户端到服务器 | 1001 |
| 服务器到客户端 | 5001 |

这次纯 ACK 不占用新的序列位置。服务器需要这次确认来完成其连接状态，不能只把三次握手解释为笼统的“测试网络能不能通”。

### 第四步：没有应用数据时，依次关闭两方向

继续使用同一连接，假设双方尚未发送应用数据，客户端先结束自己的发送方向：

| 次序 | 报文 | 接收后的关键状态 |
| --- | --- | --- |
| 1 | 客户端发 `FIN, seq=1001, ack=5001` | 服务器知道客户端不再发送，进入 `CLOSE-WAIT` |
| 2 | 服务器发纯 `ACK, seq=5001, ack=1002` | 客户端自己的 FIN 获确认，进入 `FIN-WAIT-2` |
| 3 | 服务器也准备关闭，发 `FIN, seq=5001, ack=1002` | 客户端确认另一方向结束 |
| 4 | 客户端发纯 `ACK, seq=1002, ack=5002` | 客户端进入 `TIME-WAIT`，服务器收到后可关闭 |

这些 FIN 报文也携带 ACK 标志，表中为突出结束方向只在名称写出 FIN。FIN 各消耗一个序列位置，纯 ACK 不消耗。客户端第一步发 FIN 后先处于 `FIN-WAIT-1`；服务器第三步发 FIN 后等待最后确认，处于 `LAST-ACK`。

## 为什么关闭常常比建立多一步

TCP 支持全双工（Full-Duplex）通信，即两个方向都可以传数据。客户端不再发送，不代表服务器已经发完回复。

服务器收到 FIN 后可以先确认，在自己的应用准备好之后再结束另一个方向。它若恰好也准备关闭，就可以把确认和 FIN 放进同一个报文，因此抓包不一定看到四个独立报文。

实际连接还可能同时关闭，或通过复位标志（Reset，RST）异常终止。不能把任何连接结束都强行套进上表。

## TIME_WAIT 在等什么

最大报文段生存时间（Maximum Segment Lifetime，MSL）用于限制网络中旧报文仍可能存在的时间。经典 TCP 关闭模型中，TIME_WAIT 的等待量为 `2 × MSL`。

它让最后的确认丢失时仍有机会处理对方重传的 FIN，并降低旧连接残留报文干扰后续连接的风险。收到符合规则的重传 FIN 后，需要再确认，并按协议规则处理等待计时。

本例是客户端先关闭，所以客户端进入 TIME_WAIT；角色并不固定。若服务器先关闭，服务器也可能进入该状态；同时关闭时双方也可能进入。不能把某个系统的具体秒数当成所有实现的统一常量。

## 报文丢失后并非直接跳过步骤

例如服务器发出的 SYN 与 ACK 丢失，客户端不会因此凭空知道服务器起点。相关一方会按照重传与超时规则继续处理，长期无法完成则可能连接失败。

重传超时（Retransmission Timeout，RTO）与网络测量和协议规则有关，不能理解为所有连接都每隔同一个固定毫秒数重试。握手成功也不保证后续网络永不故障。

## 常见误解

- **“三次握手证明服务器身份可信。”** 它建立传输状态，不提供网页证书那样的身份认证。
- **“每个 ACK 都让序列号加一。”** 纯 ACK 不占用序列号空间。
- **“收到 FIN 后两个方向立即都不能传数据。”** FIN 结束对应发送方向，另一方向可以继续发送剩余数据。
- **“TIME_WAIT 总属于客户端。”** 应根据关闭过程判断，不应只看业务角色。

## 选择题

某方发送一个不带应用数据的 FIN，其 `seq=200`。对端确认这个 FIN 时，确认号应为多少？

- A. 199
- B. 200
- C. 201
- D. 202

**答案：C。** FIN 占用一个序列位置，下一期望位置是 201。B 忽略了 FIN 的序列消耗；D 错把纯 ACK 本身也当作额外占用一个位置。

## 面试追问

**为什么不能只说“两次就已经确认双方能收发”？**

TCP 需要各自建立状态并确认对方的序列起点。第二步后，服务器尚未获得对自己起点的确认。解释应围绕协议状态和确认信息，而不是只数双方是否各发过一次。

**处于 CLOSE_WAIT 很久意味着什么？**

通常表示对端已经结束发送，本端仍未完成自己的关闭过程。应检查本端应用是否仍有工作、是否遗漏关闭或被其他等待阻挡；不能仅凭状态名称断言一定是网络问题。
