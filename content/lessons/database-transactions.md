# 事务：转账不能只完成一半

## 从零理解

事务（transaction）把一组数据库操作组织成一个整体，以提交（commit）或回滚（rollback）结束。
转账包含“扣除付款方余额”和“增加收款方余额”。两条语句都能单独执行，却不应各自独立成功。
如果先扣款，再因错误没能加款，余额总量就会发生不符合业务规则的变化。
事务允许这些修改一起提交，或者在放弃时一起撤销。

本课以 SQLite 和整数金额为例，单位是分，避免把浮点数舍入问题混进转账过程。
有两条已存在的账户记录：账户 1 为 1000，账户 2 为 500。目标是从 1 转 300 给 2。
“金额大于零、双方存在、余额足够”是例子的已知前提，实际程序必须检查这些条件。

## 四个性质如何落到这笔转账

事务常用 ACID 概括四个性质，各英文首字母组成这个缩写。

| 性质 | 对本例的含义 |
| --- | --- |
| 原子性（Atomicity） | 转账内修改整体生效或撤销，不只留下扣款 |
| 一致性（Consistency） | 正确事务应把数据库从符合约束的状态变成另一个符合约束的状态 |
| 隔离性（Isolation） | 并发事务之间的可见性和相互影响受数据库规则约束 |
| 持久性（Durability） | 按数据库配置成功提交的持久化数据，应能在承诺的故障范围内恢复 |

一致性不是“数据库知道转账应该怎样写”。如果把加款错误写成加 200，数据库可能正常提交这个错误逻辑。
隔离性也不表示所有数据库永远只按一种方式运行并发事务；不同系统、隔离级别和配置需要分别讨论。
浏览器中的内存数据库不提供跨页面关闭的持久保存，不能用它验证断电恢复。

## 逐步推演

### 第一步：开始事务并确认初始状态

```sql
BEGIN;
```

当前连接开始事务。两个账户余额为 `(1,1000)`、`(2,500)`，总额 1500。
开始事务不等于锁定所有世界状态；并发访问的具体限制由数据库和事务类型决定。

### 第二步：在事务内扣除 300

```sql
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
```

当前事务读取自己的修改，会看到 `(1,700)`、`(2,500)`，此刻总额暂为 1200。
这个中间状态还不应该作为完整转账的最终结果提交。
若付款账户不存在，这条语句可能影响零行，并不因此自动报错，所以程序需要核对受影响行数。

### 第三步：给账户 2 加上 300

```sql
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
```

当前事务现在看到 `(1,700)`、`(2,800)`，总额重新为 1500。
应用应确认收款方确实被更新；若收款账户不存在，必须放弃整个转账，不能继续提交扣款。
事务负责操作成组，正确检查哪些操作算成功仍是业务代码的职责。

### 第四步：选择提交或回滚

两步及检查都成功时执行 `COMMIT;`，最终余额为 700 和 800。
若在第二步后发现不能继续，就执行 `ROLLBACK;`，撤销扣款，回到 1000 和 500。

| 路径 | 账户 1 | 账户 2 | 是否保留本次修改 |
| --- | --- | --- | --- |
| 两步成功后提交 | 700 | 800 | 是 |
| 扣款后回滚 | 1000 | 500 | 否 |

不是“再加回 300”来模拟回滚；回滚由数据库按事务记录撤销未提交修改。

## 完整成功示例

以下示例用于新的 SQLite 练习数据库；两名账户、金额和余额符合前面约定。

```sql
CREATE TABLE accounts (
  id INTEGER PRIMARY KEY,
  balance INTEGER NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 1000), (2, 500);
BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
COMMIT;
SELECT id, balance FROM accounts ORDER BY id;
```

预期得到 `(1,700)`、`(2,800)`。`CHECK` 约束可以拒绝负余额，但不能证明整笔转账逻辑正确。
实际接口还要检查账户、金额、权限、受影响行数及错误，不能直接把这段固定输入示例当成完整转账服务。
测试回滚时应重新准备初始数据，执行扣款后用 `ROLLBACK` 结束，预期仍为 `(1,1000)`、`(2,500)`。

## 常见错误

- **BEGIN 后出现错误就一定全部撤销。** SQLite 的不同错误可能只撤销当前语句，也可能结束整个事务；调用方必须检查结果并正确收尾。
- **数据库没有异常就代表业务成功。** `UPDATE` 影响零行也可能是正常执行结果，却未完成转账要求。
- **事务能自动避免所有并发问题。** 必须结合实际隔离规则和读写方式设计；SQLite 同时最多允许一个写事务。
- **COMMIT 返回就能忽略任何硬件风险。** 持久性依赖存储、同步设置和故障假设，不保证错误硬件永远不丢数据。
- **回滚能撤回已经发送的邮件。** 数据库事务通常只管理自身数据修改，外部操作需要另外协调。

## 面试回答

事务将一组相关数据库操作作为整体提交或回滚。转账应把扣款和加款放在同一事务中，并确认各步满足业务条件。
ACID 分别是原子性、一致性、隔离性和持久性；数据库机制与业务约束共同维持正确状态。
具体可见性、错误行为和故障保证依赖数据库及配置，不能把“用了事务”当成全部逻辑正确的证明。

## 选择题

事务内给账户 1 扣了 300，但给账户 2 加款的 UPDATE 影响零行。此时最合适的处理是什么？

- A. 只要没有语法错误就提交。
- B. 提交后再人工找回账户 2。
- C. 视为业务失败，回滚事务并返回相应错误。
- D. 原子性保证账户 2 自动创建，所以不用处理。

**答案：C。** 收款未完成，应取消整体修改。A、B 都会留下不完整转账；D 把事务原子性误解为自动补全业务数据。

## 面试追问

“事务中的中间总额是 1200，是否破坏一致性？”中间修改尚未作为完整业务结果提交；关键是约束、隔离和最终提交状态。
“失败后重试会不会转两次？”可能，尤其无法确认第一次是否已提交时；需要另行设计业务请求标识和幂等处理。
“怎样验证原子性？”分别测试成功路径、扣款后主动回滚，以及语句失败时应用的错误收尾，而不只测试正常提交。
