# 递归与调用栈

## 面试回答

递归（Recursion）是函数直接或间接调用自身，把问题转成较小的同类问题。正确递归需要终止条件，并保证每次递归朝终止条件推进。每次调用有独立的参数和局部状态，调用栈（Call Stack）保存尚未完成的工作；最深处返回以后，外层调用再逐层继续。复杂度应分别统计总工作量与最大同时存活的调用深度，不能见到递归就断言指数时间，也不能忽略调用栈的空间。

## 从零理解

非负整数 n 的阶乘（Factorial）记作 `n!`。例如 `4! = 4 × 3 × 2 × 1 = 24`，并约定 `0! = 1`。

它具有递归关系：当 n 大于 0 时，`n! = n × (n - 1)!`。先解决较小的阶乘，再乘当前 n，就能得到当前问题的答案。

| 组成 | 本例中的规则 | 作用 |
| --- | --- | --- |
| 基本情况（Base Case） | n 为 0，直接返回 1 | 不再继续调用 |
| 递归情况（Recursive Case） | 返回 `n × factorial(n - 1)` | 把问题交给更小规模 |
| 进展保证 | 非负整数 n 每次减少 1 | 保证最终到达 0 |

仅仅写一个基本情况还不够。如果 n 从 4 开始却每次加 1，就永远到不了 0。终止条件必须和参数变化方向一起检查。

## 先读代码，再观察状态

下面的 JavaScript 示例限制为整数 `0..18`，使结果保持在 `Number` 的安全整数范围内，也避免让演示进入很深的调用层数。

```javascript
function factorial(n) {
  if (!Number.isInteger(n) || n < 0 || n > 18) {
    throw new RangeError("n must be an integer from 0 to 18");
  }
  if (n === 0) return 1;
  return n * factorial(n - 1);
}
console.log(factorial(4));
console.log(factorial(0));
```

输出依次是 `24`、`1`。调用 `factorial(-1)` 会立即抛出 `RangeError`，而不是继续向更小的负数递归。

这是输入合法性检查产生的错误，与递归太深导致的运行时调用栈错误不是同一件事。

## 逐步推演

### 第一步：外层调用保留尚未完成的乘法

执行 `factorial(4)`。n 不是 0，所以需要计算 `4 × factorial(3)`。

```text
factorial(4)：n = 4，等待 4 × 下层结果
factorial(3)：刚进入，n = 3
```

外层的 4 没有被改成 3。新调用拥有自己的参数 n，外层调用暂停等待它返回。

### 第二步：继续展开，直到基本情况

调用顺序是 `4 → 3 → 2 → 1 → 0`。到达 0 时，不再发生新的递归调用。

| 从外到内的调用 | 当前等待的工作 |
| --- | --- |
| `factorial(4)` | 4 × 下层结果 |
| `factorial(3)` | 3 × 下层结果 |
| `factorial(2)` | 2 × 下层结果 |
| `factorial(1)` | 1 × 下层结果 |
| `factorial(0)` | 直接返回 1 |

此刻同时活跃的 factorial 调用有 5 个。这里只统计本函数，不包含外部运行环境的其他栈帧。

### 第三步：先返回内层，再完成外层

调用栈遵循后进先出的返回次序。每个栈帧（Stack Frame）保存该次调用需要的状态。

| 正在完成的调用 | 计算 | 返回值 |
| --- | --- | --- |
| `factorial(0)` | 基本情况 | 1 |
| `factorial(1)` | `1 × 1` | 1 |
| `factorial(2)` | `2 × 1` | 2 |
| `factorial(3)` | `3 × 2` | 6 |
| `factorial(4)` | `4 × 6` | 24 |

“调用自己”不是所有层同时直接拿到 24。每层都接收下层的返回值，再完成自己剩下的乘法。

### 第四步：分别数工作量和最大深度

输入 4 时共有 5 次 factorial 调用、4 次阶乘乘法，最大同时活跃调用数为 5。

把这一递归结构推广到规模 n，并按一次乘法为 O(1) 的单位成本模型分析：调用 n + 1 次，时间为 Θ(n)；没有尾调用消除时，最大深度 n + 1，辅助栈空间为 Θ(n)。

上述渐近分析讨论算法结构，不是在说 JavaScript `Number` 可以精确表示任意大的阶乘。如果改用任意精度整数，数值位数不断增长，乘法成本也要重新计入。

## 活跃调用栈实验

实验把可选 n 限制为 0 到 7，以便完整展示每一层。每次进入都新增一个保存独立 n 的栈帧，每次返回都移除最内层栈帧，并把返回值交给外层继续乘法。画面显示的是算法状态，而不是读取浏览器引擎内部的真实调用栈。

观察 `factorial(0)` 时仍会出现一个栈帧，只是它直接返回 1，不再调用自己。观察 `factorial(4)` 时，最大活跃深度是 5，最终返回值是 24；栈清空意味着本次调用全部返回，不意味着计算结果被删除。

## 为什么会发生栈溢出

运行环境可用的调用栈空间有限。没有正确终止，或者虽然终止但深度过大，都可能导致栈溢出（Stack Overflow）。

例如某些 JavaScript 引擎会报告 `RangeError: Maximum call stack size exceeded`，另一些会报告 `InternalError: too much recursion`。不能把某个引擎的报错文本或可承受深度当成所有环境的统一标准。[MDN 递归过深错误](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Errors/Too_much_recursion)

递归改写为循环时，可以把待处理状态放入显式栈。这样能更主动地管理状态，但如果仍需保存同样多的待处理工作，空间复杂度不会自动变成 O(1)。

## 常见误区

- **“每层 n 都是同一个变量。”** 不同调用有各自的参数状态，内层 n 不会覆盖外层 n。
- **“写了基本情况就一定终止。”** 还要证明递归参数能到达它，并处理非法输入。
- **“递归一定是指数时间。”** 本例每层只递归一次；分支数量和重复子问题才会改变总工作量。
- **“没有显式数组，就不占额外空间。”** 普通递归仍使用调用栈保存状态。
- **“尾递归一定不会溢出。”** 是否消除尾调用取决于语言和运行时保证，不能默认；本例返回前还要做乘法，也不是尾递归。

## 选择题

按照本课代码执行 `factorial(4)`，不计外部环境，在首次到达基本情况时，有多少个 factorial 调用尚未完全返回？

- A. 1
- B. 4
- C. 5
- D. 24

**答案：C。** 活跃调用分别是参数为 4、3、2、1、0 的五层。B 漏掉基本情况那次调用；D 把数值结果当成调用数量。每层返回后，对应的待处理状态才能被释放。

## 面试追问

**阶乘能不能改成循环？改完有什么变化？**

可以用累积变量从 1 依次乘到 n，0 的情况直接保留初值 1。在相同单位成本模型下，时间仍为 Θ(n)，但不再保存 n 层调用，辅助空间可降到 O(1)。这来自阶乘只需一个累积状态，不能推广成“任何递归改循环都只要常数空间”。
