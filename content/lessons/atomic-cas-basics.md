# CAS 怎样避免两个线程都把计数写成 1

## 先看丢失更新

计数器初始为 0。A 和 B 都先读到 0，各自算出 1，然后普通写入 1，最终可能仍是 1。**比较并交换**（Compare-And-Swap，CAS）把“比较当前值是否等于期望值，若相等则写入新值”做成一个原子操作；失败者不能仍按旧观察值继续写。[Go：sync/atomic](https://pkg.go.dev/sync/atomic)

实验里 A、B 都先准备 `CAS(期望 0, 新值 1)`：A 成功后计数变 1，B 的期望值 0 已过时，故失败；B 重新读取 1，准备 `CAS(1,2)` 才能成功。只做一次 CAS 不保证业务总能成功，通常需要在竞争时重试，但重试策略也应避免无界空转。

## 为什么它不等于万能锁

CAS 保证**这一处比较与写入**不可被交错打断，不保证“同时修改余额和账单两处状态”作为整体原子。即使单个值先变 A、又变 B、再回 A，只比当前值的 CAS 也可能看不出中途变化，这叫 ABA 问题；是否需要版本号等措施取决于算法。Go 的 `CompareAndSwapInt64` 返回是否交换成功；其他语言的 API 对失败时如何更新期望参数可能不同。[Go：sync/atomic CompareAndSwapInt64](https://pkg.go.dev/sync/atomic#CompareAndSwapInt64)

## 面试回答

CAS 原子地检查当前位置是否仍等于期望值，若相等才写入目标值，返回成功或失败。两个线程都从 0 计算加一时，第一个 CAS 可把值改为 1，第二个用旧期望 0 会失败，必须重读并重算才能改为 2。它能用于单值无锁更新，但失败要处理，且不能自动保护跨多个变量的不变量。

## 常见误区

- **“CAS 失败也会写入目标值。”** 失败不会完成该次交换。
- **“CAS 永远比锁快。”** 高竞争下反复失败可能浪费 CPU。
- **“原子计数器让整个订单流程原子。”** 只覆盖被该原子操作管理的状态。

## 选择题

计数器已被 A 从 0 CAS 到 1，B 仍执行 `CAS(0,1)`，结果是什么？

- A. 成功，计数变 2
- B. 失败，计数仍为 1
- C. 成功，计数变 0
- D. B 自动修改期望值为 2

**答案：B。** 当前值 1 不等于期望值 0；B 需要重新读取并准备新目标。
