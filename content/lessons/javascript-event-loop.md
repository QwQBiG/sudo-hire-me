# JavaScript：为什么输出顺序不是代码顺序？

## 从零理解

函数是一段可以稍后调用的代码。回调函数（callback function）是交给其他代码在适当时机调用的函数，交出函数不等于已经执行它。
`console.log("A")` 现在就调用打印操作；`() => console.log("B")` 则先创建一个函数。
只有后者真正被调用时，才会打印 `B`。

调用栈（call stack）记录目前正在执行的函数及其返回位置。
例如函数 `outer` 调用 `inner` 时，要先完成 `inner`，才能回到 `outer` 继续。
队列保存等待处理的工作；等待中的回调没有占着调用栈执行。
浏览器负责计时等宿主能力，JavaScript 回调需要等到合适的执行机会。

本课限定为下面这段代码，不包含用户点击、网络请求或其他脚本。网页实验在隔离的工作线程（Web Worker）的异步函数体中运行；本例没有 `await`，初始同步执行段不会提前让出执行权。
事件循环（event loop）协调后续工作；任务（task）与微任务（microtask）是两类调度工作，“宏任务”是面试材料对 task 的常见称呼。
Promise 表示一次操作的最终成功值或失败原因；本课只用已成功兑现的 Promise，完整状态与错误处理放在下一课。
浏览器存在不同任务来源，不能把全部真实调度简化成一条永远固定的总队列。
理解本例只需要分清：当前同步执行、Promise 微任务、后续定时器任务。

## 实验代码

下列代码可以完整运行。先写下四个字母的顺序，再对照输出。

```javascript
console.log("A");
Promise.resolve().then(() => console.log("B"));
setTimeout(() => console.log("C"), 0);
console.log("D");
```

`Promise.resolve()` 得到一个已兑现的 Promise，但 `then` 回调仍不会在登记时直接调用。
`setTimeout` 登记一个计时请求，并立即返回；它不会在原地阻塞脚本等待。

## 一步一步推演

| 步骤 | 此刻发生的事 | 已输出 |
| --- | --- | --- |
| 1 | 执行第一行的打印 | A |
| 2 | 为已兑现 Promise 登记 B 回调，安排微任务 | A |
| 3 | 登记定时器，C 回调等待后续执行机会 | A |
| 4 | 执行最后一行的同步打印 | A D |
| 5 | 当前同步执行段结束，在微任务检查点执行 B 回调 | A D B |
| 6 | 后续轮到定时器任务，执行 C 回调 | A D B C |

这张表解释调度语义，不是在测量每一步耗费多少毫秒。
即使计时条件已经满足，C 也不能插进当前这段同步代码中间。
微任务优先处理不代表它可以打断正在执行的同步代码。

## 预期输出

```text
A
D
B
C
```

代码输出显示的是执行顺序；仅凭这四行不能推断页面何时完成绘制。
浏览器会安排渲染机会，但并非每个任务之后都会实际绘制一帧。

## 改一个条件

把 Promise 那一行改成下面这一行，再保留其余三行：

```javascript
(() => console.log("B"))();
```

现在 `B` 在创建函数之后被立即调用，属于当前同步执行段。
输出变为 `A B D C`。决定时机的是如何调用函数，而不是函数写在第几行。
再把原例的定时器放到 Promise 前面，原例的输出仍为 `A D B C`。
原因是当前同步代码结束后先处理已安排的微任务，C 仍作为后续任务执行。

## 常见错误

- **“Promise 都是异步执行的。”** `new Promise(executor)` 的 executor 会同步调用；本课异步的是 `then` 回调。
- **“微任务一定马上执行。”** 微任务要等相应检查点，不会抢占当前同步代码。
- **“延迟是 0，就应该先打印 C。”** 0 不会取消调度约束，当前同步执行段与微任务仍需先处理。
- **“写进 async 函数就不卡页面。”** 耗时同步计算仍会占用当前执行线程，`async` 不自动创建工作线程。
- **“不停添加微任务可以提升响应。”** 持续补入微任务可能推迟后续任务和渲染机会。

## 面试回答

在浏览器的同一 JavaScript 执行线程上，当前同步执行段先执行完。
已兑现 Promise 的 `then` 回调作为微任务等待执行；定时器回调作为后续任务等待调度。
在相应的微任务检查点，微任务队列会被处理，因此本课先输出同步结果，再输出 Promise 回调结果，最后输出定时器结果。
`setTimeout(fn, 0)` 不表示立即调用 `fn`，也不承诺精确的执行时刻。

## 选择题

运行最初的四行代码，哪个判断正确？

- A. 输出 `A B C D`，因为脚本逐行执行，所以回调也逐行完成。
- B. 输出 `A D C B`，因为 0 毫秒定时器优先于 Promise。
- C. 输出 `A D B C`，同步代码先完成，然后处理微任务和后续定时器任务。
- D. B 和 C 谁先输出不确定，因为它们必定在两个线程上同时执行。

**正确答案：C。**

- A 错在把“执行登记回调的语句”当成“执行回调函数”。
- B 错在把计时延迟当成调度优先级，0 不能跳过微任务检查点。
- C 正确，分别对应本例的同步代码、微任务和定时器任务。
- D 错在把异步直接等同于并行；这些回调在本例同一执行线程上先后执行。

## 面试追问

保留原来的 Promise 和定时器，在 `console.log("D")` 前增加一个有限但耗时的同步循环。
B 和 C 的先后会改变吗？它们是否可能在循环执行到一半时输出？为什么？

参考思路：本例仍为 `A D B C`；循环延迟 D 以及后续回调的执行，不会为 B、C 主动让出执行机会。
应解释“当前同步执行没有结束”，而不只说“JavaScript 是单线程的”。
浏览器还具有其他线程和 Worker；本题讨论的是这段脚本所属的执行线程。
