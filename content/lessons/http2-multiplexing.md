# HTTP/2 怎样在一条连接上交错传响应

## 三个层次先分开

HTTP/2 在一条连接上使用**流**（Stream）承载独立的双向消息，每个流又由带流标识的**帧**（Frame）组成。不同流的帧可以交错发送，接收方按流标识分别重组；同一流内的帧仍有顺序语义。这是应用层的**多路复用**（Multiplexing），不是把 TCP 变成多个物理连接。[RFC 9113：HTTP/2](https://www.rfc-editor.org/rfc/rfc9113.html)

下列 `A1` 等只是说明交错的教学标签，不是实际 HTTP/2 二进制帧格式。流 1 的响应含 A1、A2；流 3 的响应含 B1、B2。

## 逐步推演

### 先送 A1，再送 B1

接收端看到 `(流1,A1) → (流3,B1)`。流 1 尚未完成，并不妨碍流 3 的一部分先到达。

### 接着送 A2、B2

线上的次序是 `A1 → B1 → A2 → B2`；按流重组后，流 1 为 `A1+A2`，流 3 为 `B1+B2`。不能把 B1 拼进流 1，也不能仅凭发送交错推断哪个响应一定先完成。

### 假设承载 A2 的 TCP 字节丢失

TCP 按序向上交付字节；丢失的数据在重传补齐前，后续到达的字节也可能无法被 HTTP/2 层读取，即使它们属于流 3。这是单条 TCP 连接上的传输层队头阻塞（Head-of-Line Blocking）；HTTP/2 解决了 HTTP/1.1 在连接上顺序处理响应带来的应用层限制，但没有消除 TCP 这一层的影响。[RFC 9113：Streams and Multiplexing](https://www.rfc-editor.org/rfc/rfc9113.html)

## 面试回答

HTTP/2 把请求和响应拆成带流 ID 的帧，多个流的帧可在一条连接上交错传输，接收方按 ID 重组，因此慢响应不必在应用层挡住另一响应的帧发送。不过底层仍是一条有序 TCP 字节流，发生丢包时依然可能出现连接级队头阻塞。多路复用也不代表无限并发，实际并发流数量受协商和实现限制。

## 常见误区

- **“一条 TCP 连接只能有一个 HTTP 请求。”** HTTP/2 可在同一连接承载多个并发流。
- **“帧交错后响应内容会混在一起。”** 帧有流标识，按流重组。
- **“HTTP/2 彻底没有队头阻塞。”** 仍可能受 TCP 层丢包影响。

## 选择题

若线上帧顺序为 `(1,A1),(3,B1),(1,A2),(3,B2)`，流 3 的完整内容是什么？

- A. `A1A2`
- B. `A1B1A2B2`
- C. `B1B2`
- D. `A2B2`

**答案：C。** 帧在连接上可以交错，但接收方按流 ID 分别重组；流 3 只取 `B1`、`B2`。把所有帧直接按到达顺序拼接会混入流 1 的 `A1`、`A2`。
