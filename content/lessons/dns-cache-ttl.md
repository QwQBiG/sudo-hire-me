# DNS 记录改了，旧 IP 为什么还会出现

## TTL 管的是缓存，不是连接

DNS 资源记录中的 **TTL**（Time To Live）指定缓存数据再次咨询来源前允许保留的时间。这里讨论普通正向 A 记录缓存；负面回答等有额外规则。TTL 为 0 表示该记录不应跨当前事务缓存。TTL 不是“域名查询必须在多少秒内完成”，也不是已经建立的 TCP 连接的生命周期。[RFC 1035：Resource Record Format](https://www.rfc-editor.org/rfc/rfc1035.html)

假设权威服务器在时刻 0 回答 `demo.example → 192.0.2.10`，TTL 为 60 秒；某递归解析器立即缓存。时刻 45，权威记录改为 `192.0.2.20`，新答案也设 TTL 60 秒。以下只算**这个解析器**的缓存，不假定浏览器、操作系统或别的解析器的缓存状态。

## 逐步推演

### 时刻 0：写入旧答案

缓存持有 `192.0.2.10`，剩余寿命 60 秒。下游若再次询问，解析器可以用缓存回答。

### 时刻 40 和 45：先命中，再修改权威记录

时刻 40 缓存剩 20 秒。时刻 45 权威源改为 `192.0.2.20`，但已有缓存不会因为权威记录变化就自动被统一清空；此解析器旧答案约还剩 15 秒。

### 时刻 61：重新查询

原缓存已经过期；若此时向权威链重新取到新记录，才缓存 `192.0.2.20`。具体查询时刻可能晚于过期时刻，个别解析器也可能实施标准允许的特殊缓存策略，不能承诺全球用户在第 60 秒同时切换。[RFC 8767：Serving Stale Data](https://www.rfc-editor.org/rfc/rfc8767.html)

## 面试回答

DNS 记录的 TTL 约束缓存记录的有效时间。权威侧更新 IP 后，之前缓存的旧答案仍可能在剩余 TTL 内被返回；缓存过期后的新查询才通常得到新值。不同缓存层的获取时刻不同，应用也可能复用已有连接，所以不能把 TTL 当成所有用户切换 IP 的精确倒计时。

## 常见误区

- **“改权威记录后所有客户端立刻看到新 IP。”** 已缓存的答案不会统一被推送替换。
- **“TTL 60 秒表示变更后还要固定等 60 秒。”** 每个缓存项按自己先前的获取时刻计时。
- **“TTL 到 0 就会断开旧连接。”** DNS 缓存与已建立的连接是两件事。

## 选择题

按本课的单个解析器示例，时刻 50 查询最可能从尚未过期的缓存得到什么？

- A. `192.0.2.10`
- B. `192.0.2.20`
- C. 一定是 NXDOMAIN
- D. 两个地址会自动合并

**答案：A。** 旧记录在时刻 0 缓存 60 秒，时刻 50 仍在有效期内。
