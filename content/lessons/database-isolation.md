# 隔离级别：同一事务为什么读到不同余额

## 从一个具体问题开始

账户余额最初是 100。事务 A 读取一次，事务 B 随后把余额改成 120 并提交，A 再读取一次。
A 的两次查询属于同一事务，第二次一定还是 100 吗？答案取决于隔离级别和查询方式。
隔离级别（Isolation Level）约定并发事务之间允许观察到哪些现象，不只是“是否用了 BEGIN”。

本课只讨论同一条记录的普通 SELECT，不包含加锁读取、A 自己写入、数据库连接失败等情况。
交互参照 PostgreSQL 的快照语义进行教学模拟，没有连接真正的 PostgreSQL，也不是 SQLite 的隔离级别选择器。
理解结论时，需要同时记住数据库、隔离级别与读取类型这三个前提。

## 先区分两种现象

脏读（Dirty Read）指事务读取了另一个事务尚未提交的修改。
如果 B 改成 120 后最终回滚，A 却已经根据 120 做了判断，A 使用的就是没有成为已提交事实的数据。

不可重复读（Non-repeatable Read）指同一事务再次读取同一数据时，因其他事务提交修改而得到不同结果。
这里两次读到的都可能是已提交值。不可重复读不要求出现脏数据，两者不是同义词。

幻读（Phantom Read）关注按同一条件重复查询时，符合条件的记录集合发生变化。
例如第一次查询余额大于 100 的账户有两条，其他事务插入符合条件的记录并提交，第二次变成三条。
本课的交互只修改一条已有记录，用来展示不可重复读，不把所有结果变化都称作幻读。

## 读已提交怎样读取

读已提交（Read Committed）要求看不到其他事务未提交的修改。
在 PostgreSQL 中，一条普通 SELECT 读取该语句开始时已经提交的数据快照；同一事务内下一条 SELECT 可以获得新快照。
快照（Snapshot）是这个读取视角下可见的数据版本，不必理解成把整张表复制到内存。

| 时刻 | 执行操作 | 已提交余额 | A 本次读到 |
| --- | --- | --- | --- |
| 1 | A 第一次 SELECT | 100 | 100 |
| 2 | B UPDATE 为 120，尚未提交 | 100 | 尚未查询 |
| 3 | A 再次 SELECT | 100 | 100 |
| 4 | B COMMIT | 120 | 尚未查询 |
| 5 | A 再次 SELECT | 120 | 120 |

时刻 3 没有读到 B 的未提交值，所以没有脏读。
时刻 5 与时刻 1 的结果不同，所以发生不可重复读。这符合读已提交的保证，不是数据库违反承诺。

## 可重复读怎样保持稳定

可重复读（Repeatable Read）进一步保证本课中的同一记录重复读取不会因为其他事务提交而改变。
PostgreSQL 在此级别中使用事务快照：快照在事务的第一条非事务控制语句开始时确定，后续普通查询沿用它。
在本例中第一条这样的语句就是 A 的第一次 SELECT，而不是单独执行 BEGIN 的时刻。

仍按上表顺序操作，A 三次读取都是 100，即使 B 已经提交 120。
120 没有丢失；新的事务可以看见它，只是 A 仍在自己的既定快照中读取。
如果 B 先提交，A 才执行第一次 SELECT，那么 A 的快照可以包含 120，之后继续读到 120。

多版本并发控制（Multiversion Concurrency Control，MVCC）通过保留数据版本，帮助读操作选择可见版本。
它不是“所有操作都不加锁”，也不表示旧版本永远保留；具体版本管理、清理和锁规则取决于实现。

## 用两个 PostgreSQL 会话复现

先在练习数据库准备一张只有一行的表，确保没有其他程序修改它：

```sql
CREATE TABLE isolation_demo (id INTEGER PRIMARY KEY, balance INTEGER);
INSERT INTO isolation_demo VALUES (1, 100);
```

会话 A 先执行：

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM isolation_demo WHERE id = 1;
```

第一次查询应得到 100。保持 A 的事务不结束，在会话 B 执行：

```sql
BEGIN;
UPDATE isolation_demo SET balance = 120 WHERE id = 1;
COMMIT;
```

回到会话 A，再执行相同 SELECT，应得到 120，最后执行 COMMIT 结束事务。
要测试可重复读，先在所有事务结束后把余额恢复到 100，再把 A 的 BEGIN 改为：

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

重复相同操作顺序，A 的第二次查询应仍得到 100。
以上是依据 PostgreSQL 文档推导的双连接复现流程；页面交互是状态模型，不能替代真实数据库并发验证。

## 一张稳定快照还不能保证什么

如果两个事务各自读取“至少还有一名值班人员”，然后分别把不同人员设为离岗，可能各自满足判断却共同破坏规则。
这类跨记录约束不能只靠“重复读取同一快照”就自动成立，仍需结合更强隔离、锁或业务约束设计。
本课不模拟这个场景，但它说明可重复读不能直接等同于所有事务按顺序执行。

可串行化（Serializable）要求成功提交的并发结果等价于某种串行执行顺序。
这不意味着数据库只允许一个事务运行。实现可以允许并发，再在发现冲突时中止某些事务，应用需要处理重试。

## 常见错误

- **两次读到不同值就是脏读。** 如果新值已经提交，这是不可重复读，不是脏读。
- **BEGIN 之后所有数据库都立刻拍快照。** 快照建立时机依数据库、隔离级别和语句而异。
- **隔离级别的名字相同，实现细节必然相同。** 例如 SQL 标准层面的可重复读允许幻读，而 PostgreSQL 的此级别不允许幻读，但仍可能出现序列化异常。
- **只要开启 MVCC 就不会有锁。** 多版本读取与锁可以同时参与并发控制。
- **浏览器 SQL 实验可以直接执行上面的 PostgreSQL 命令。** 内置运行器使用 SQLite，不支持这套同名语法与双会话流程。

## 面试回答

读已提交避免读取其他事务未提交的修改，但同一事务的多条查询仍可能读到其他事务新提交的版本，发生不可重复读。
可重复读进一步保持本课中的重复读取稳定；PostgreSQL 普通查询会沿用首次非事务控制语句建立的事务快照。
隔离名称要结合数据库实现解释，稳定快照不等于所有业务约束都自动安全，可串行化事务也可能需要冲突重试。

## 选择题

A 第一次读取余额 100；B 把余额改成 120 并提交；A 在同一事务再次读到 120。最准确的判断是什么？

- A. 这是脏读，因为结果发生变化。
- B. 这是幻读，因为第二个值原先不存在。
- C. 这是不可重复读；两次读到的值都可以是已提交值。
- D. 任何支持事务的数据库都不允许这种现象。

**答案：C。** 同一条记录因其他事务提交修改而改变，符合不可重复读。脏读要求读到未提交修改，幻读关注条件查询的记录集合变化；事务保证必须结合隔离级别讨论。

## 面试追问

“可重复读为什么还能读到自己刚写入的数据？”事务通常能看见自己的修改，不能把对其他事务的快照规则机械套到自身写入。
“读已提交为什么还有价值？”不少业务接受每条查询读取最新已提交视图；是否足够要依据业务不变量，而不是只追求名称更强。
“如何排查线上并发错误？”记录数据库版本、隔离级别、语句、事务边界和交错顺序，再构造最小双连接复现。
