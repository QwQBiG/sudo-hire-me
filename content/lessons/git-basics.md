# Git：add 之后再修改，会提交哪一版

## 从零理解

Git 是分布式版本控制系统（distributed version control system），记录项目内容随时间的变化。
提交（commit）记录项目的一份快照及相关历史信息，不是把文件直接发给远程服务器。
本地提交与远程传输是不同操作；`git push` 才会尝试把相应历史发送到远程仓库并更新引用。

理解普通提交，先区分三个位置：

| 位置 | 含义 |
| --- | --- |
| 工作区（working tree） | 当前实际编辑的文件内容 |
| 暂存区（staging area，也称 index） | 下一次普通提交准备记录的内容 |
| 当前提交（由 HEAD 指示） | 当前检出的历史快照，本课用作比较基线 |

`git add` 把指定文件当前内容加入暂存区，不是给文件贴上“以后所有修改自动进入提交”的标签。
普通 `git commit` 根据暂存内容创建新提交；`git commit -a` 等形式会改变这个流程，本课不使用。
HEAD 在通常分支工作流中通过当前分支定位到提交；不要把它理解成一个普通源代码文件。

## 例题的初始条件

已有仓库中的 `notes.txt` 是被跟踪文件，当前提交与暂存区、工作区内容都为 `version A`。
接下来先编辑成 B，暂存，再编辑成 C；问题是普通提交会保存 B 还是 C。
这里的 A、B、C 表示文件内容的版本，不是 Git 分支名称。
下面所有状态都是这个具体操作序列的教学推演，不是在操作某个真实项目。

## 逐步推演

### 第一步：把工作区内容改成 B

| HEAD 快照 | 暂存区 | 工作区 |
| --- | --- | --- |
| version A | version A | version B |

此时只有工作区改变。`git diff -- notes.txt` 比较工作区与暂存区，会显示 A 到 B 的变化。
`git diff --cached -- notes.txt` 比较暂存区与当前提交，目前没有差异。

### 第二步：执行 add，把当前 B 暂存

```powershell
git add -- "notes.txt"
```

| HEAD 快照 | 暂存区 | 工作区 |
| --- | --- | --- |
| version A | version B | version B |

此时暂存区准备提交 B。普通 `git diff` 为空，而 `git diff --cached` 显示 A 到 B。
`--` 结束命令选项解析，其后明确给出文件路径。

### 第三步：继续把工作区改成 C

| HEAD 快照 | 暂存区 | 工作区 |
| --- | --- | --- |
| version A | version B | version C |

这次编辑没有自动更新暂存区。`git diff` 现在显示 B 到 C，`git diff --cached` 仍显示 A 到 B。
同一个文件可以同时包含“已暂存的变化”和“尚未暂存的变化”。
本例执行 `git status --short`，预期该文件的状态为 `MM notes.txt`。

### 第四步：确认提交范围

在不再 add、也不使用自动暂存选项的前提下，普通提交记录 B，工作区中的 C 会继续保留。
如果想记录 C，需要先重新把该文件的 C 版本加入暂存区，再核对暂存差异。
选择提交哪个版本是内容选择问题，不取决于哪个版本最后被编辑器显示过。

## 读懂比较命令

```powershell
git status --short
git diff -- "notes.txt"
git diff --cached -- "notes.txt"
git diff HEAD -- "notes.txt"
```

| 命令 | 第三步时的比较 | 本例含义 |
| --- | --- | --- |
| `git diff` | 暂存区 B 与工作区 C | 尚未暂存的改动 |
| `git diff --cached` | HEAD 中 A 与暂存区 B | 普通提交将记录的改动 |
| `git diff HEAD` | HEAD 中 A 与工作区 C | 相对于当前提交的总体变化 |

`status --short` 的第一状态列比较暂存区与 HEAD，第二状态列比较工作区与暂存区；本例两列 M 都表示修改。
这些 diff 示例针对已跟踪文件。新建但尚未跟踪的文件会在 status 中出现，普通 diff 不会自动显示其全部内容。

## 提交与推送的边界

暂存操作没有创建提交，因此还没有新的提交编号。
提交记录到本地仓库后，即使没有网络，也可以继续查看本地历史。
推送是与远程仓库的协作操作；可能因为权限、网络或远程已前进而失败。
“本地文件已保存”“已暂存”“已提交”“已推送”是四个不同状态，汇报时应说清楚。

## 常见错误

- **add 后所有编辑都会自动提交。** add 记录调用时选中的内容，后续编辑需要另行暂存。
- **diff 为空就表示工作区完全干净。** 还可能有已暂存改动或未跟踪文件，应结合 status 检查。
- **commit 会上传文件。** 普通提交是本地历史操作，上传涉及推送。
- **Git 永远只存逐行补丁。** Git 的概念模型是快照，内部存储可能采用压缩等机制，不等于工作模型只有补丁。
- **为了提交一个文件应该 add 整个目录。** 应按实际提交范围选择路径，并检查完整暂存差异。

## 面试回答

工作区保存正在编辑的文件；暂存区组织下一次普通提交；提交记录到本地历史中。
git add 把选定内容放入暂存区，之后继续编辑不会自动改变已暂存版本。
用 git diff 看未暂存差异，用 git diff --cached 看准备提交的差异，再结合 status 确认文件状态。

## 选择题

把 notes.txt 从 A 改为 B 并执行 add，再改为 C，直接执行不带自动暂存选项的普通 commit，会记录什么？

- A. C，因为它是磁盘上最新内容。
- B. A，因为 add 不影响版本记录。
- C. B，因为暂存区仍保存 B。
- D. B 与 C 自动合成的内容。

**答案：C。** 普通提交以暂存区为输入。A 忽略了暂存快照；B 忽略已暂存的修改；D 假设了不存在的自动合并。

## 面试追问

“怎样确认没有把临时修改混进提交？”检查 status 和完整暂存 diff，而不只看编辑器当前文件。
“为什么需要暂存区？”一次工作过程中可能有多项改动，暂存区让开发者选择这次提交所表达的逻辑变化。
“push 成功是否等于测试通过？”不等于，历史传输与行为验证是不同事实。
