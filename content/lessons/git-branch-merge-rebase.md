# 两条开发线怎样重新汇合

## 分支是指向提交的引用

Git 分支（Branch）可以理解为指向某个提交的可移动名字，不是复制出一整套独立文件。你在功能分支继续提交，分支指针向前移动；主分支有新提交时，两条历史可能从共同祖先处分叉。合并（Merge）与变基（Rebase）都能让功能分支纳入主分支的改动，但它们**处理历史的方式不同**。[Git 文档：git-merge](https://git-scm.com/docs/git-merge)、[Git 文档：git-rebase](https://git-scm.com/docs/git-rebase)

以下都只画提交关系，不表示必须立刻运行命令。设共同祖先是 B，功能分支做了 C、D，主分支做了 E：

```text
      C -- D   feature
     /
A -- B -- E   main
```

## 逐步推演

### 第一步：先找共同祖先与各自新提交

B 是两条线共有的最后提交；C、D 只在 feature，E 只在 main。此时只切换到 main 并不会自动拥有 C、D，也不会把 E 自动放进 feature。面试中“合并分支”应明确从哪个分支合入哪个分支，不能只报 `merge` 一个词。

### 第二步：merge 保留分叉再汇合

在 feature 上合入 main，若 Git 需要真正的合并提交，可得到 M，M 有来自 D 与 E 的两个父提交：

```text
      C -- D -- M   feature
     /         /
A -- B ------- E   main
```

C、D、E 原提交仍在原位置。若两边修改冲突，必须解决冲突后完成合并；merge 不会因为保留历史就自动保证没有冲突。若历史没有分叉，Git 也可能直接快进（Fast-forward）移动分支指针，不一定产生 M。本例有分叉，才用合并提交展示概念。[Git 文档：git-merge](https://git-scm.com/docs/git-merge)

### 第三步：rebase 把改动重放到新基底

在 feature 上以 main 为新基底变基，Git 会尝试把 C、D 的改动依次重放在 E 之后。结果可表示为 `A -- B -- E -- C' -- D'`；C' 与 D' 是**新的提交对象**，并非把原 C、D 在原位置直接移动。提交身份改变，故不能随意变基一个其他人已经基于它继续工作的共享分支。[Git 文档：git-rebase](https://git-scm.com/docs/git-rebase)

变基每一步也可能遇到冲突，需要解决并继续；它不是“自动解决冲突”的工具。最终文件内容是否与某次 merge 完全相同，要看如何处理冲突和改动，并不能只凭两种命令推断。

### 第四步：按协作约束选路径

如果需要保留分支的真实汇合记录，merge 很直接；如果是**自己尚未共享的功能分支**，想把提交整理为基于最新 main 的线性历史，可以在确认团队约定后 rebase。已经公开、被同事基于其提交继续工作的历史，改写会让双方提交身份不一致，需要特别谨慎。选型还可能受到仓库合并策略和评审规则限制，不能说“所有团队都应该只用一种”。

## 面试回答

分支是指向提交的引用。历史分叉后，merge 通常保留原有分叉并创建汇合提交；rebase 将当前分支的改动重放到新基底，生成新的提交身份，让历史更线性。两者都可能遇到冲突。对已经与他人共享的提交，我不会不经协调就变基改写；具体使用方式取决于团队的评审与历史约定。

## 看图时不要忽略结果验证

无论哪种路径，完成后都要检查提交图、差异和测试。提交图说明代码从何而来，但不保证业务行为正确；冲突解决尤其可能引入“编译通过却行为变了”的问题。合并策略讨论的是历史与协作成本，不是质量测试的替代品。

## 常见误区

- **“merge 总会新增合并提交。”** 可快进时未必需要。
- **“rebase 不产生新提交。”** 重放后的提交身份通常改变。
- **“rebase 可以自动消除冲突。”** 冲突仍可能逐个出现。
- **“只要我本地能成功，改写共享分支就没有影响。”** 他人可能已基于旧提交工作。

## 选择题

主分支新增 E，功能分支已有 C、D；你对尚未共享的功能分支执行 rebase，使其基于 E。哪项正确？

- A. 原来的 C、D 一定保持完全相同的提交身份。
- B. Git 尝试把 C、D 的改动重放在 E 之后，产生新的提交；过程中仍可能有冲突。
- C. rebase 会自动替你运行所有业务测试并保证正确。
- D. rebase 等于删除主分支的 E。

**答案：B。** 变基重放提交而非移动原提交对象；A、C、D 分别误解提交身份、验证和新基底。
