# 错误日志怎样帮助找到真正失败的位置

## 日志是事件证据，不是魔法答案

日志（Log）记录程序运行时发生的事件。只打印“error”通常不足以定位问题：不知道哪次请求、哪个阶段、什么输入类别、什么失败原因。结构化日志（Structured Logging）把事件名、时间、请求标识、阶段、结果等放在独立字段中，便于过滤和关联；这不表示必须采用某一种特定 JSON 格式或日志平台。

假设一次创建订单请求经过入口验证、价格计算、数据库写入，最后返回错误。日志的目标不是把整个订单对象和用户资料都打出来，而是让维护者能回答：哪个请求失败、到达了哪一步、失败发生在哪个受控边界。[OpenTelemetry：Logs Data Model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)

## 逐步推演

### 第一步：没有关联标识时会混淆请求

两位用户几乎同时提交订单。日志按时间交错：`开始创建`、`数据库超时`、`开始创建`、`创建成功`。若没有请求标识，很难判断超时属于哪一单。给每次请求一个可传播的 `request_id`，同一请求的入口、服务和数据库边界都带上它，就能按标识重建路径。标识应帮助关联，不应直接使用敏感的身份证号或完整访问令牌。

```text
request_id=R17 event=order.received
request_id=R18 event=order.received
request_id=R17 event=order.store.failed reason=timeout
request_id=R18 event=order.completed
```

这样能知道 R17 失败而 R18 成功，但还不能凭 `timeout` 一词断言数据库本身坏了；可能是连接池耗尽、网络延迟、锁等待或超时阈值设置。日志提供线索，仍需结合更多证据。

### 第二步：字段要能回答排障问题

对 `order.store.failed`，有用字段可能包括 `request_id`、阶段、错误类别、耗时毫秒和重试次数。若只写一整段不可解析文字，检索“所有超过某阈值的 store.failed”会更难；若把完整订单内容和密钥写入日志，又会增加泄露风险。字段设计应先问：排障时想按什么维度查？这个字段是否允许被记录和保留？

| 字段 | 帮助回答 | 注意 |
| --- | --- | --- |
| `request_id` | 哪些事件属于同一次请求 | 不用敏感信息直接充当 ID |
| `stage` / `event` | 失败前走到哪里 | 名称保持稳定一致 |
| `duration_ms` | 哪段操作耗时 | 明确单位与起止范围 |
| `error_kind` | 哪类失败 | 避免只剩“未知错误” |

### 第三步：级别表达严重程度，但不是固定真理

常见日志级别有 DEBUG、INFO、WARN、ERROR。调试细节可以用 DEBUG，正常完成事件可用 INFO；可恢复但值得关注的异常可用 WARN；一次操作失败可用 ERROR。具体约定由团队决定，不能把“所有超时都必须 ERROR”当作跨系统标准。如果请求失败却被记录为 INFO，告警和排查可能遗漏；如果每次预期的输入校验失败都记录为严重系统故障，又会淹没真正问题。

级别不是根因分类。`ERROR` 只能表明这个事件被视为错误，仍要看上下文和实际影响。

### 第四步：避免日志本身成为新问题

高频循环中无节制记录大对象会增加 I/O 和存储压力。密码、访问令牌、私人数据不应为方便调试直接输出；必要字段要脱敏并符合系统的数据保留规则。故障时还要检查日志是否丢失、时间戳是否可比、不同服务的 `request_id` 是否正确传播。日志缺席不等于事件没有发生。

## 面试回答

我会把日志当作可检索的运行事件：记录稳定事件名、请求标识、阶段、结果、耗时单位和错误类别，用标识串起同一次请求。级别按团队约定区分调试信息、正常事件、警告与失败，但不靠级别代替根因分析。避免记录密钥和不必要的个人数据，排障时再结合指标、调用链与实际复现。

## 日志能证明到哪里

本例四行日志能说明 R17 在保存阶段失败、R18 完成；它不能直接说明全部请求的失败比例，也无法仅凭错误文本确定超时为何发生。统计比例需要有明确分母和时间窗口，跨服务耗时路径通常还要看调用链或额外时间数据。

## 常见误区

- **只打印“出错了”。** 缺少请求与阶段上下文。
- **以日志级别代替影响分析。** ERROR 标签不说明有多少请求受到影响。
- **把完整敏感输入写入日志。** 方便一时可能造成长期泄露风险。
- **没有日志就断言没有发生。** 采集、采样或程序崩溃都可能造成缺失。

## 选择题

两条订单请求的日志交错，你想知道某次数据库超时属于哪条请求。最直接需要什么？

- A. 给同一请求的各阶段记录可关联的请求标识。
- B. 把所有日志级别改为 ERROR。
- C. 记录每位用户的完整密码。
- D. 删除正常完成事件，只留下“失败”二字。

**答案：A。** 可传播的关联标识能把交错事件按请求串起；B 不建立对应关系，C 有安全风险，D 丢失路径上下文。
