# HTTP 请求与 HTTPS 保护

## 面试回答

超文本传输协议（Hypertext Transfer Protocol，HTTP）规定请求与响应的语义，包括方法、目标资源、头部和状态码；它可以传输网页、结构化数据和其他内容。安全的 HTTP（HTTP Secure，HTTPS）用于受到保护的 HTTP 通信，通常借助传输层安全协议（Transport Layer Security，TLS）提供机密性、完整性和所需的对端身份验证。HTTPS 不保证业务权限正确或网站内容可信。HTTP 的语义与具体传输映射需要区分：常见 HTTP/1.1、HTTP/2 使用传输控制协议（Transmission Control Protocol，TCP），HTTP/3 使用 QUIC，不能说所有 HTTPS 都先进行 TCP 握手。

## 从零读懂一个网址

统一资源定位符（Uniform Resource Locator，URL）描述资源的位置及访问方式。以 `https://www.example.com/items/7?color=blue#details` 为例：

| 部分 | 值 | 含义 |
| --- | --- | --- |
| 方案 | `https` | 使用受保护的 HTTP 访问 |
| 主机名 | `www.example.com` | 用于定位服务并参与身份检查 |
| 端口 | 省略 | 本方案的默认端口为 443 |
| 路径 | `/items/7` | 目标资源路径 |
| 查询部分 | `color=blue` | 随请求目标传给服务器的信息 |
| 片段 | `details` | 客户端使用，不作为 HTTP 请求目标发给服务器 |

端口号只是默认约定，可以显式指定其他端口。服务器怎样解释 `/items/7` 取决于应用，并不表示服务器磁盘上必定存在同名文件。

## 请求和响应分别有哪些信息

请求方法（Method）表达对资源要做什么；请求头部（Header Fields）补充格式、认证、缓存等信息；消息体（Message Body）在需要时承载内容。

响应状态码（Status Code）表达处理结果的类别，头部描述内容和处理要求，消息体返回实际内容。HTTP 不等于页面标记语言，也不要求每条消息都带正文。

下面推演一次**首次建立 HTTP/1.1 over TLS over TCP 连接**的情况，省略代理、连接复用和恢复握手。TCP 提供这里需要的字节流；不能把此流程推广成所有 HTTP 版本的固定顺序。

## 逐步推演

### 第一步：解析目标并取得地址

客户端从 URL 分离主机名、端口、路径和查询信息，经域名系统（Domain Name System，DNS）取得服务器地址。假设本例得到教学地址 `192.0.2.20`。

```text
连接目标：192.0.2.20:443
服务器身份：www.example.com
请求目标：/items/7?color=blue
不发送为请求目标的部分：#details
```

连接使用地址，不表示身份检查就可以只比较 IP。正常访问此域名时，还需要验证对端是否适用于该服务器名字。

### 第二步：建立传输并完成安全握手

本例先建立 TCP 连接，再进行 TLS 握手。采用常见证书认证场景，逻辑上需要完成：

| 工作 | 解决的问题 |
| --- | --- |
| 协商协议与密码参数 | 双方使用兼容的保护方式 |
| 检查证书和认证消息 | 验证所需服务器身份与密钥关联 |
| 密钥协商与确认 | 建立用于后续数据保护的密钥材料 |

表格是职责划分，不表示每行恰好对应一个独立网络报文。验证证书要考虑域名、信任链、有效期等要求；不能把“对方发来一张证书”视为验证通过。

### 第三步：发送受保护的 HTTP 请求

握手成功后，客户端发送请求。下面展示应用层可读的消息形式，不是旁观者能从加密流量中直接看到的明文：

```http
GET /items/7?color=blue HTTP/1.1
Host: www.example.com
Accept: application/json

```

`GET` 表示获取资源的表示；`Host` 表明请求的主机；`Accept` 表示客户端希望接收的内容类型。这里没有请求正文，也没有把片段 `details` 发给服务器。

### 第四步：解释响应，再交给应用使用

假设服务器找到目标资源，返回以下教学响应；正文为 JavaScript 对象表示法（JavaScript Object Notation，JSON）格式：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 8

{"id":7}
```

该正文按这里的编码恰好为 8 字节，示例不包含额外正文换行。客户端先获得通过传输保护检查的数据，再按状态、头部和 JSON 格式解释结果。`200` 表示本次请求成功，不表示之后所有请求都一定成功。

## GET 的安全和幂等是什么意思

安全方法（Safe Method）的请求语义不以修改服务端状态为目的，例如 GET。服务器仍可能记日志，所以“安全”不是“执行时绝不写任何数据”，更不是“内容已经加密”。

幂等（Idempotent）关注重复相同请求的预期效果是否与执行一次相同，不要求每次响应内容都相同。GET 具有安全、幂等的语义；POST 用于按目标资源的规则处理提交内容，协议层不普遍保证其幂等。

提交订单常用 POST，但超时后仍需业务判断是否可以重试。传输安全、方法语义和业务去重解决的是不同问题。

## HTTPS 保护什么，又不保证什么

| 保护目标 | 含义 | 不能推出的结论 |
| --- | --- | --- |
| 机密性（Confidentiality） | 未授权旁观者不应读到受保护内容 | 对端应用不会泄露内容 |
| 完整性（Integrity） | 传输内容遭到篡改时能够检测 | 服务器返回的业务数据必定正确 |
| 身份验证（Authentication） | 按协议和验证规则确认所需身份 | 该网站的所有行为都值得信任 |

HTTPS 不解决服务器把秘密写入公开日志的问题，也不代替“这个用户能否读取这份数据”的权限判断。通信地址及部分握手元信息仍可能可见，不能认为整个通信事实都被隐藏。

应用数据通常使用协商出的对称密钥保护，不能概括为“所有 HTTP 内容都用证书里的公钥逐字加密”。

## HTTP/3 为什么不是先建 TCP

HTTP/3 将 HTTP 语义映射到 QUIC。QUIC 使用用户数据报协议（User Datagram Protocol，UDP）承载，并结合 TLS 1.3 的握手与密钥机制提供安全传输能力。

因此，同样是 `https://` 地址，也可能采用 HTTP/3。HTTPS 描述受保护的 HTTP 访问，不能仅从地址前缀推断底层一定是 TCP。

## 常见误解

- **“POST 的正文看不见，所以天然安全。”** POST 本身不提供加密；GET 与 POST 都需要合适的传输与访问保护。
- **“HTTP 无状态，服务器就不能保存登录状态。”** 协议的无状态语义不禁止应用另外管理会话。
- **“404 是网络连接完全没建立。”** 收到 404 本身就是得到了一份 HTTP 响应，应从目标资源和应用处理继续检查。
- **“证书有效，网站内容就一定真实。”** 身份验证与业务内容可信程度是两件事。

## 选择题

关于 HTTPS，以下哪项正确？

- A. 所有 HTTPS 请求都必须先进行 TCP 三次握手
- B. 它能保护传输，但不能代替服务器的业务权限检查
- C. 只要使用 POST，就不需要 TLS
- D. 证书有效就能证明网站返回的全部内容都正确

**答案：B。** A 忽略 HTTP/3 与 QUIC，C 把请求方法误当加密机制，D 把对端身份验证误当业务真实性证明。

## 面试追问

**为什么收到 500，与请求超时的含义不同？**

500 是服务器返回的 HTTP 错误响应；超时是客户端未在规定时间内得到所期待的结果。超时不能单独证明服务器没有收到或执行请求，排查时需要区分传输阶段与应用阶段。
